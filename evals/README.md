# 评测

目的不是证明它好，是让"变好"这件事可测。没有这一步，改 `SKILL.md` 全靠感觉。

## 三个数

| 指标 | 怎么算 | 现在 |
|---|---|---|
| 判型准确率 | 主型判对 / 总数 | 未测 |
| 边界准确率 | `scope` 判对 / 总数 | 未测 |
| 依据错标率 | 把「假设」标成「推断」或「措辞推断」的格数 / 总格数 | 未测 |

前两个看它听没听懂，第三个看它诚不诚实。**第三个最重要**——错标依据不会让结果变差，会让用户失去纠正的机会。

"识别率"这个词太粗，拆成这三个才能定位：判型错了补语料，边界错了改可达集，依据错标改规则表述。三个数一起掉，说明改坏的是流程。

## 怎么跑

1. 从 `cases.md` 取一条输入
2. 按 `SKILL.md` 走一遍，**只看第一层**
3. 对照期望列，记三个数
4. 结果写进 `scoreboard.md`

跑全部用例，半小时能完。

## 用例怎么加

**每错一次加一条。** 这是唯一会持续变快的办法——改提示词只改一次，加语料能一直涨。

一条用例至少要有四项：输入、期望判型、期望边界、必须出现 / 不许出现的东西。

## 产出对比

上面三个数只测第一层。第二层的效果没法自动测，只能做 A/B：同一个任务，A 直接做，B 走一遍 skill，两份产出摆一起看差在哪。

一个月一次就够，但必须**别人看**。自己写自己评一定看不出问题，这是这个项目最容易自嗨的地方。

## 已知限制

- **答案和题放在一起**：语料与金标签都在技能目录里，被测 agent 理论上能读到。现在靠在指令里禁止，那是软约束。要真正隔离，得把 `evals/` 和 `assets/golden/` 挪出技能 bundle，测试时单独挂载。
- **判型口径没统一**：`ambiguity_type` 有时写单型、有时写 `T2+T7`。打分前先定：包含主型算对。
- **一次跑四条不够**：金标签只有四条，而且都是 `in` / `in-degraded`，没有 `out`。四个数好看不代表能用。

## 分数公开

开源时把 `scoreboard.md` 贴进 README。这比写"效果好"有说服力，也比藏起来安全：数字难看的时候至少知道该改哪儿。
