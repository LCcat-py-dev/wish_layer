# wish-layer · 许愿翻译层

> 把"说不清"翻译成"能执行"。

给 AI 加一层前置判断：先看用户的请求模糊在哪，能补就补并标出依据，补不了就问一两个真正改变结论的问题，最后把结果编译成可执行的提示词。

## 它解决什么

许愿式编程降低了"写代码"的门槛，没降低"说清楚要什么"的门槛。真实的请求长这样：

> 我想要一个网站
> 帮我做个能卖东西的网页
> 做个网站，要高级一点

现有工具默认用户会给出一份合格的需求。这个默认在大多数人身上不成立。

## 跟提示词美化器的区别

美化器只会把话变长。这一层会**反驳**：

| 用户说 | 美化器给的 | 这一层给的 |
|---|---|---|
| 帮我做个能卖东西的网页 | 一份电商系统需求 | 字面是团队数月的活，你大概是要挂几样东西收款——是这个意思吗 |
| 做一个像小红书那样的 | 罗列小红书的功能清单 | 参照物是平台不是需求，先拆成七个能独立回答的面 |
| 做个网站，要高级一点 | 保留"高级"这个词 | 转译成留白 / 字号层级 / 配色数量 / 动效，且先问"给谁看" |

四件事撑起这个差别：

- **判型**——先判断这是哪一种"说不清"，再决定能不能直接补
- **依据可见**——每一格标清是推出来的、猜的，还是用户亲口说的
- **敢降级**——说的和要的差一个数量级，就摆出来，不顺着扩写
- **敢说不知道**——骨架里没有对应位置时判 `unknown`，不许就近安放

## 结构

```
SKILL.md                    入口：每次都要的判断流程和输出格式
references/
  methods.md                判型、流程、契约、铁律
  domain-pack.md            写新领域包的规范
  domains/web/
    pack.md                 网站包：判域、槽位、复杂度、可达集
    catalog.md              C / R / M 速查表
assets/golden/              4 条金标签（完整需求单）
evals/                      用例、语料、分数、历次跑分记录
notes/                      提取记录、收件箱
FOR-AI.md                   给 AI 读的：能拿什么、别拿什么
```

分层加载是刻意的：`SKILL.md` 只放每次都要的，细节和领域知识按需读。默认路径约 6000 字，全读约 11000 字。

## 怎么用

**直接用**：把整个目录放进 agent 的 skills 根目录（例如 `~/.dsh/skills/`），新开会话即可。

**抄结构**：`SKILL.md` + `references/methods.md` 这一对是跟领域无关的，换任何领域都能用。领域相关的东西全在 `domains/` 下。

**换领域**：按 `references/domain-pack.md` 的九项清单，自己写一个包——判域标准、槽位表、填充规则、复杂度公式、可达集、形容词转译、路线方案、语料、骨架。

## 实测

| 指标 | 结果 |
|---|---|
| 判型准确率 | 5/5 |
| 边界准确率 | 5/5 |
| 依据错标率 | 0/67 |
| 依据缺标 | 4/67 |

**这些数字别当真。** 只有 5 条用例，而且都是同一个领域的，跑分记录在 `evals/runs/`。真正的价值在那两份记录里：第一跑抓出了 T1/T4 边界糊，第二跑抓出了降级方向写反——都是靠用例发现的，不是靠读代码看出来的。

## 已知局限

- 只有一个领域包（网站），换个领域要重写
- 语料和金标签来自与 AI 的对话，**不是真实用户样本**
- `unknown` 分支只被构造过一条用例
- 第二层（编译）几乎没被真实跑过——所有用例都停在提问

## 来源

- 判定机制（T1–T8、依据分级、三级边界）整理自 2026-11 的一份参赛方案
- 语料由 AI 生成，非用户调研
- 本项目在人机协作下完成，文档与代码均有 AI 参与
